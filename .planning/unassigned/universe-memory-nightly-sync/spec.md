### Data model changes

`storyGroups` (the "universe" table) gains one nullable column: `style_guide_synced_at timestamp`. No default, no backfill required — `null` is a meaningful, valid state ("never synced by this mechanism") that the sync function branches on explicitly. Generated via `drizzle-kit generate`, applied via `npm run db:migrate` (neon-http driver) per project CLAUDE.md — never `drizzle-kit migrate` directly, and never pushed by hand.

### Decisions made autonomously

- **Consolidate persistence into `synthesize-universe-memory.ts` itself, called by all three triggers** (nightly, manual, on-read), rather than leaving each caller to persist independently. Reason: the overwrite bug exists precisely because persistence logic is duplicated at each call site; fixing it in one place and having every caller defer to it is the only way to guarantee no caller regresses back to overwrite behavior later.
- **Do not unify with `updateStyleGuide`/`style-guide-updater.ts`.** Reason: different trigger (approval vs. schedule/read/manual), different input granularity (one story's structured analysis vs. a multi-story raw feedback delta). Both already merge-not-overwrite once this change lands, so the pre-existing "two writers, same columns" situation is no longer a data-loss bug, just an accepted last-write-wins interleaving (see architecture.md Failure modes). Unifying them is a larger refactor with its own risk profile and isn't required by any done-when criterion.
- **Delta cursor (`styleGuideSyncedAt`) only advances on an actual write.** Reason: if it advanced every run regardless, a run finding nothing new would move the cursor forward anyway, risking silently skipping feedback whose `createdAt` lands just behind a fast-moving cursor under clock/commit-order skew. Leaving it untouched when there's nothing to fold in is simpler and strictly safer, and is what makes SCENARIO 2 a true no-op.
- **Nightly job runs the per-universe loop synchronously in-process within the single scheduled request, not fanned out via Cloud Tasks.** Reason: `catalog-sync`, the only existing scheduled job in this app, already establishes in-process as the pattern; this is a single-family personal app with a small number of universes, so Cloud Tasks fan-out (built for the auto-pipeline's heavier per-story generation work) is unwarranted complexity here.
- **Cron time `0 4 * * *` UTC**, one hour after `catalog-sync`'s `0 3 * * *`. Reason: arbitrary but deliberate stagger to avoid two scheduled jobs hitting the same Cloud Run service at the same instant; trivially reconfigurable later.
- **Manual endpoint keeps its 422-on-nothing-to-sync contract.** Reason: confirmed via repo-wide search that no frontend code currently calls `/universes/:id/synthesize-memory`, so there is no UI contract to preserve or break — 422 is kept only because it's the smallest possible diff to today's behavior, not because anything depends on it.
- **Extensibility for the not-yet-built story-chat feedback source is structural, not a new abstraction.** Reason: the delta-query step already reads from four independent tables and folds each into one prompt; adding a fifth (chat comments) later means adding one more parallel query and one more prompt section inside the same function — no plugin registry or generic "feedback source" interface is introduced now, since that would be speculative plumbing for a feature that doesn't exist yet (per the task's own constraint).
- **Plan auto-confirmed by grand-loop (no human present to review) — Medium/Complex path, consistency gate passed with 0 gaps** (all 8 checks: scenario→acceptance, deriver→scenario, scenario→coverage, diagram→scenario, todo→spec, constitution, scenario→files-by-scenario, documentation).

### Scope boundary

Out of scope for this task:
- Unifying `updateStyleGuide`/`style-guide-updater.ts` with the new sync engine (see Decisions made autonomously).
- Any locking/concurrency-control mechanism for overlapping writers to the same `storyGroups` row (accepted last-write-wins, per SCENARIO 9).
- Building the story-chat feedback source itself — only the structural room for adding it later (a fifth parallel query) is preserved, per the task's own constraint against speculative plumbing.
- Any notification to the user that a nightly sync ran or updated a universe's memory (not requested by the done-when criteria; the character/trait-extraction wishlist item is where a notification channel is explicitly being considered).
- Cloud Tasks fan-out for the nightly loop (see Decisions made autonomously).
- Widening the story window beyond the existing "last 50 ready/read stories" cap. This is a pre-existing limitation carried forward unchanged from today's `synthesizeUniverseMemory` — feedback left on a story older than the 50 most recent in its universe was already invisible to synthesis before this change, and stays that way. Not a regression introduced here; revisiting the window size is a separate, independent decision.
