## Iteration 23 — Robust JSON extraction + schema-aware candidate selection
- **Problem:** `extractJsonFromText` used a non-greedy fence regex that grabbed the FIRST fenced block unconditionally, and `raw.lastIndexOf('}')` for the brace fallback. If a plotter/critic/psychologist response contained an example block followed by the real answer, the extractor silently picked the example. If the response had two adjacent JSON objects, it sliced across both and produced invalid JSON. If a string literal contained a `}`, the naive `lastIndexOf` still worked but was luck, not correctness. Any of these killed the pipeline run with `AiValidationError` and no recovery.
- **Fix:** New generator `jsonCandidates(raw)` yields candidates in priority order: `json`-labeled fences first, then plain fences, then a balanced-brace object (respecting string literals and escapes), then the trimmed raw text. `runStructured` now iterates candidates and returns the FIRST one that both parses AND validates against the Zod schema — so a leading example block with the wrong shape no longer shadows the real answer. Falls back to `AiValidationError` only after all candidates fail.
- **Tests:** 8 new unit tests covering priority ordering (json fence before plain, multiple fences emitted, balanced fallback), string-literal safety (`}` in strings, escaped quotes), and multi-object inputs (stops at first balanced close). Existing extractor tests still pass because `extractJsonFromText` now returns the first candidate. Full suite 73 green across 7 files. Typecheck clean.
- **Status:** Ready to commit.

## Iteration 21 — Snapshot accuracy: stop pre-writing text-phase columns at plan time
- **Problem:** `persistPlanPhase` inserted the run_snapshots row with writerModel, writerPromptVersion, psychologistTextModel, psychologistTextPromptVersion, writerCriticModel, and writerCriticPromptVersion already filled from `plan.models`/`plan.promptVersions`, even though the writer and writer-critic stages had not yet run. If the default writer model or prompt version changed between plan phase and text phase (server restart with new defaults, Improver bumping a prompt version), the snapshot would silently misattribute model/prompt choices to the wrong phase. That corrupts the Improver's feedback → prompt mapping at the source.
- **Fix:** New pure module `pipeline-persistence.ts` exposes four row-builder functions — `buildPlanSnapshotInsert`, `buildTextSnapshotUpdate`, `buildPlanStoriesUpdate`, `buildTextStoriesUpdate`. Plan builder only writes plotter/psychologist-plan/plot-critic columns; text builder writes writer/psychologist-text/writer-critic columns + text outputs when the text phase actually completes. `persistPlanPhase` and `persistTextPhase` are now two-liners that delegate to the builders. Type-only imports from orchestrator.ts mean the tests don't trigger env validation.
- **Tests:** 6 new unit tests verify that plan insert leaves text-phase columns undefined and vice versa, plus the stories-table updates are correct. Full suite now 59 green across 6 files. `tsc --noEmit` clean.
- **Status:** Ready to commit.

## Iteration 20 — Guard approve-plan against re-running completed text phase
- **Problem:** `POST /stories/:id/approve-plan` only consulted the in-memory `pipelineStatusMap` to decide whether to trigger `runTextPhase`. After a server restart (in-memory map empty) a double-click or late polling request would re-run the entire text phase even though `stories.text_v2` already holds the completed story. `persistTextPhase` then overwrote the existing snapshot and stories row with a brand-new (and different) text — wasted model cost plus silent data loss for the story Sasha was going to hear tonight.
- **Fix:** New pure module `approve-plan-decision.ts` with `decideApprovePlan(story, inMemoryStatus)` returning one of `start_text_phase | skip_already_running | skip_already_complete | reject`. DB is authoritative for completion: if `textV2` is non-null, the route skips triggering regardless of in-memory state. `text_failed` still allows retry so users can recover from transient AI failures. Route handler just dispatches on the decision — all the branching logic is unit-tested.
- **Tests:** 10 new unit tests covering plan_missing, seed_missing, already-complete (including stale in-memory state), already-running, already-ready, text_failed retry, and fresh start paths. Full suite now 53 green across 5 files. `tsc --noEmit` clean.
- **Status:** Ready to commit.

## Iteration 16 — Architecture: plan/text phase split with human gate
- **Problem:** Orchestrator ran the entire pipeline (plotter → iterations → writer → critic → writer) in one shot. By the time user saw plan-review, text was already generated. Approve-plan was a no-op — the documented human gate was bypassed.
- **Fix:** Split `runPipeline` into `runPlanPhase` (plotter + iterations + psychologist + critic) and `runTextPhase` (writer + critic + writer). `POST /pipeline/run` now triggers plan phase only. `approve-plan` triggers text phase in background. `persistPlanPhase` writes plan outputs to DB; `persistTextPhase` updates the same snapshot row with text outputs.
- **Granular statuses:** `plan_running | plan_ready | plan_failed | text_running | text_ready | text_failed`. Frontend pipeline page distinguishes them and shows "Review Plan" or "Review Text" button at the right time. plan-review approval navigates back to the pipeline page to watch text phase.

## Iteration 17 — Architecture: DB-backed prompt resolution
- **Problem:** Architecture specified DB-versioned prompts so the Improver could iterate prompts without code deploys. Stages had hardcoded prompts and ignored the `prompts` table entirely.
- **Fix:** New `prompt-resolver.ts` module with `resolvePrompt(agent, fallback)` that queries the prompts table for the latest version and falls back to hardcoded default on empty/missing/error. Orchestrator resolves prompts once per phase and passes the resolved text + actual version to each stage. Snapshots now accurately reflect the prompt version that was actually used.
- **Tests:** Unit tests for resolvePrompt covering DB hit, miss, empty text, custom fallback version, and DB-error fallback paths.
- **Status:** Committed as c8dd10e.

## Iteration 18 — Idempotency guards + DB-fallback status
- **Problem 1:** Double-clicking "Create Story" or "Approve Plan" would trigger two pipeline phases against the same storyId in parallel, racing on the snapshot row.
- **Fix 1:** `POST /pipeline/run` returns 409 when a pipeline is already active or completed for the story. `approve-plan` skips re-triggering when text phase is already running or ready. Committed as a3bd08c.
