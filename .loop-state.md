## Iteration 34 — Frontend API client now surfaces backend error messages
- **Problem:** `request()` in `packages/web/src/lib/api.ts` threw `API error ${status}: ${statusText}` on any non-2xx response and discarded the response body. Every backend route returns `{ error: 'specific reason' }` (we just made sure of that in rounds 28 and 31), but the user never saw those reasons — they saw generic "API error 500: Internal Server Error" or "API error 400: Bad Request" regardless of whether the real problem was `"Plan has not been generated yet; cannot approve"` or `"Invalid agent name"` or `"Rating is required"`. This broke every form, every approve button, and every pipeline trigger when things went wrong.
- **Fix:** New pure helper `format-api-error.ts` extracts `body.error` or `body.message` when the parsed JSON body contains one, falls back to `statusText`, then to a bare status code. `request()` now attempts `res.json()` on non-OK responses (swallowing JSON parse errors as null) and builds the error message through `formatApiError`. Every existing error-display site (`FeedbackForm`, `plan-review`, `text-review`, `create-story-modal`, `story-reader` annotation toolbar) instantly gets the real backend message.
- **Tests:** 9 new unit tests for `formatApiError`: body.error path, body.message fallback, error-preferred-over-message, null body, string body (non-JSON), empty error field, empty-statusText-and-body, non-string error fields, and defensive no-throw on weird shapes. Full suite 148 green across 14 files. Typecheck clean.
- **Status:** Ready to commit.

## Iteration 33 — Real LCS-based diff so plan/text reviews show useful changes
- **Problem:** `DiffViewer.computeDiff` was a naive index-by-index line comparison. Any insertion or deletion shifted all subsequent lines, and every single one was marked removed+added even though nothing downstream had actually changed. For plan-review (comparing `plan_v1` → `plan_final`) and text-review (`text_v1` → `text_v2`), this meant the human reviewer saw a wall of red/green that obscured the actual changes. If the plotter inserted a single new scene at position 3 of a 7-scene plan, the user saw all 5 remaining scenes flagged as changed — making it impossible to tell what the critic actually fixed.
- **Fix:** Extracted the diff logic into a pure `line-diff.ts` module that implements a real LCS-based line diff — builds the LCS matrix in O(n*m), backtracks to produce added/removed/unchanged operations, reverses for chronological output. `DiffViewer` now imports `computeLineDiff` from it. Pure, no dependencies, small (~50 lines).
- **Tests:** 11 new unit tests covering identical inputs, pure insertion (start/middle/end), pure deletion, line replacement, the key regression case (one-line insertion mid-block shouldn't mark every later line as changed), empty inputs on either side, and completely disjoint inputs. Full suite 139 green across 13 files. Typecheck clean.
- **Status:** Ready to commit.

## Iteration 31 — FeedbackForm shows submission errors instead of silently eating them
- **Problem:** `FeedbackForm.handleSubmit` wrapped `await onSubmit(result.data)` in a `try/finally` that reset `loading`, but caught no errors. If the `/api/stories/:id/feedback` POST rejected (500, validation, network), the rejection escaped as an unhandled promise (the caller invoked via `void handleSubmit()`), the form's `error` state was only used for client-side validation, and the user saw the loader stop and the form sit there with no indication anything had failed. For the read-to-Sasha flow this is especially bad — the user types a thoughtful post-read comment, submits, and thinks it's saved when it isn't.
- **Fix:** Added a `catch` branch that sets `error` to the thrown message (or a generic fallback) before `finally` resets loading. Does not clear `comment` or `rating` on failure so the user can retry without retyping. Matches the approve-plan / approve-text error handling pattern already in place.

## Iteration 30 — MemoryQueue no longer wedges on a single handler error
- **Problem:** `MemoryQueue.drain()` (intended as the backbone of the future Improver / pipeline queue) had two latent bugs. First, if the handler rejected for any job, the `while` loop threw out of drain and `this.running` was never reset to `false` — every subsequent `enqueue` call would push items into `pending` and return without processing them, because `drain` always returned early. One transient error → dead queue forever. Second, if jobs were enqueued before `process()` attached a handler, they sat there until a future enqueue happened to retrigger drain. Not yet wired into the live pipeline, but the Improver auto-trigger backlog item depends on this primitive.
- **Fix:** `drain()` now uses `try/finally` to always reset `running`, and each handler call is wrapped in its own `try/catch` that logs the error and continues the drain. `process()` now explicitly kicks off a drain so pre-queued jobs start flowing as soon as a handler is supplied. Behavior for the happy path is unchanged.
- **Tests:** New `memory.queue.test.ts` with 5 tests: FIFO happy path, handler-error-continues-drain, handler-error-does-not-wedge (re-queue after throw still runs), late-attached handler drains existing backlog, and concurrent-drain safety (no double-processing when enqueue happens mid-drain). Full suite 119 green across 11 files. Typecheck clean.
- **Status:** Ready to commit.

## Iteration 29 — Improver now shares runStructured's multi-candidate JSON parser
- **Problem:** The Improver stage bypassed `runStructured` and hand-rolled `runText` + `extractJsonFromText` + `JSON.parse` + `safeParse`. Both paths are now schema-aware and automatically skip malformed or wrong-shape candidates.

## Iteration 23 — Robust JSON extraction + schema-aware candidate selection
- **Problem:** `extractJsonFromText` used a non-greedy fence regex that grabbed the FIRST fenced block unconditionally, and `raw.lastIndexOf('}')` for the brace fallback. If a plotter/critic/psychologist response contained an example block followed by the real answer, the extractor silently picked the example. If the response had two adjacent JSON objects, it sliced across both and produced invalid JSON. If a string literal contained a `}`, the naive `lastIndexOf` still worked but was luck, not correctness. Any of these killed the pipeline run with `AiValidationError` and no recovery.
- **Fix:** New generator `jsonCandidates(raw)` yields candidates in priority order: `json`-labeled fences first, then plain fences, then a balanced-brace object (respecting string literals and escapes), then the trimmed raw text. `runStructured` now iterates candidates and returns the FIRST one that both parses AND validates against the Zod schema — so a leading example block with the wrong shape no longer shadows the real answer. Falls back to `AiValidationError` only after all candidates fail.
- **Tests:** 8 new unit tests covering priority ordering (json fence before plain, multiple fences emitted, balanced fallback), string-literal safety (`}` in strings, escaped quotes), and multi-object inputs (stops at first balanced close). Existing extractor tests still pass because `extractJsonFromText` now returns the first candidate. Full suite 73 green across 7 files. Typecheck clean.
- **Status:** Ready to commit.
