## Iteration 16 — Architecture: plan/text phase split with human gate
- **Problem:** Orchestrator ran the entire pipeline (plotter → iterations → writer → critic → writer) in one shot. By the time user saw plan-review, text was already generated. Approve-plan was a no-op — the documented human gate was bypassed.
- **Fix:** Split `runPipeline` into `runPlanPhase` (plotter + iterations + psychologist + critic) and `runTextPhase` (writer + critic + writer). `POST /pipeline/run` now triggers plan phase only. `approve-plan` triggers text phase in background. `persistPlanPhase` writes plan outputs to DB; `persistTextPhase` updates the same snapshot row with text outputs.
- **Granular statuses:** `plan_running | plan_ready | plan_failed | text_running | text_ready | text_failed`. Frontend pipeline page distinguishes them and shows "Review Plan" or "Review Text" button at the right time. plan-review approval navigates back to the pipeline page to watch text phase.
- **Tests:** New vitest tests for `runPlanPhase`, `runTextPhase`, `runPipeline`, and `toPublicStatus`. Mock stages directly with `vi.mock`.
- **Status:** Committed as 6aa447e.

## Iteration 17 — Architecture: DB-backed prompt resolution
- **Problem:** Architecture specified DB-versioned prompts so the Improver could iterate prompts without code deploys. Stages had hardcoded prompts and ignored the `prompts` table entirely.
- **Fix:** New `prompt-resolver.ts` module with `resolvePrompt(agent, fallback)` that queries the prompts table for the latest version and falls back to hardcoded default on empty/missing/error. Orchestrator resolves prompts once per phase and passes the resolved text + actual version to each stage. Snapshots now accurately reflect the prompt version that was actually used.
- **Tests:** Unit tests for resolvePrompt covering DB hit, miss, empty text, custom fallback version, and DB-error fallback paths.
- **Status:** Committed as c8dd10e.

## Iteration 18 — Idempotency guards + DB-fallback status
- **Problem 1:** Double-clicking "Create Story" or "Approve Plan" would trigger two pipeline phases against the same storyId in parallel, racing on the snapshot row.
- **Fix 1:** `POST /pipeline/run` returns 409 when a pipeline is already active or completed for the story. `approve-plan` skips re-triggering when text phase is already running or ready. Committed as a3bd08c.
- **Problem 2:** Pipeline status map is in-memory; after a server restart the frontend polls 'pending' forever even though stories.plan_final or stories.text_v2 is persisted.
- **Fix 2:** `GET /pipeline/status/:storyId` now falls back to inferring status from the stories table when the in-memory map has no entry. text_v2 → text_ready, plan_final → plan_ready. Active in-memory state still takes precedence. Committed as f8f15f5.
